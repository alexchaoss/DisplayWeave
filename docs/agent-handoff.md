# DisplayWeave development handoff

Snapshot: October 13, 2026, America/Toronto. **Treat the "next steps" list as proposals, not as a request to start work.**

## User intent and current status

The goal is software that confines fullscreen applications to customizable, non-overlapping ultrawide regions while leaving the physical desktop and taskbar alone. The user asked to avoid interfering with games in ways that could violate their terms; no game compatibility, anti-cheat or terms-of-service approval has been established.

On October 11 the user moved the experimental virtual-display prototype off `main`: it lives on the `prototype` branch, with its own handoff, report, architecture notes and fixtures. `main` holds only the hook-based app.

## Evidence

After the October 11 preset and resident-component changes: managed 103 (layout 20, rules 42, automatic 13, lifecycle 28), native policy 223 + IPC on x64 and x86, installer 20, setup 6, plus live checks on the real display with owned probes. Details in [[testing.md](testing.md)](../[testing.md](testing.md)).

0.5.6 crashed the user's browser: once the resident-hook fix let automatic handling attach, Chromium stopped itself with a deliberate breakpoint. Chromium windows (class `Chrome_WidgetWin_*`) are never hooked from 0.5.8 and get only the outside maximize fit; Status & help lists them as **Ready** before they are maximized (`ChromiumWindowProtection`, native `RS_IsChromiumWindowClass`). Chromium resets any move of its maximized window in `WM_WINDOWPOSCHANGING`, so the outside fit passes `SWP_NOSENDCHANGING` (`FitFlags`). Without it, the user's Chromium-based apps filled the whole display when maximized. At the user's request, File Explorer folder windows (`CabinetWClass`, `ExploreWClass`) get the same outside-only fit, even in the shell's process (`ShellProcessProtection.IsFolderWindow`, `OutsideOnlyReason`); the desktop, taskbar and all other shell windows stay excluded and are never hooked. The outside fit cannot avoid one full-width frame (Windows maximizes before anyone outside the app can act); `MaximizeWatcher`, an out-of-context `EVENT_OBJECT_LOCATIONCHANGE` hook, ticks as soon as a window maximizes, which cut the flash from up to 250 ms to about 16 ms. Measured on screen, Windows' maximize animation then hides that frame; disabling the window's DWM transitions shows it, so animations are left alone (user decision, 2026-10-11). `v0.5.6-preview` was published by CI and has this problem.

A resident component is reused only when its control mapping (`Local\DisplayWeave_<pid>`) exists, never because a module is named `RegionHook.dll`. Any other `RegionHook.dll` (pre-rename RegionScreen builds; a later protocol, once its names change as `RegionProtocol.h` asks) stays inactive beside a freshly loaded component. A live resident worker also takes over another window of its process. The installed 0.5.5 refused the user's browser with error 1306 because it held an October 9 pre-rename hook; after installing 0.5.6 a helper attached there without a restart. Presets are computed from the display's size, aspect ratio and scaling (`RulerLayout.PresetPins`): Wide center on the user's 7680 × 2100 work area at 125% is 1980 | 3720 | 1980.

Status & help lists handled apps with their display, region and status; selecting a row shows the exact error. An error while handling one app leaves only that app alone, and the others stay handled. Only an engine error outside any app pauses handling; window errors are reported without pausing. A layout whose display is missing says so instead of showing "Handling active". A first start no longer pauses itself. While RegionScreen 0.5.4 runs, DisplayWeave sees its renamed displays (`\\.\REGIONSCREEN1..3`) and cannot resolve its layout. On October 11 RegionScreen 0.5.4 was uninstalled at the user's request with its own quiet uninstaller: its sign-in and uninstall entries are gone, its settings folder was kept, and two hook DLLs still loaded in running apps are deleted at the next sign-in. The pre-rename RegionScreen Prototype (`%LOCALAPPDATA%\RegionScreenPrototype`) is still installed. DisplayWeave 0.5.9-preview (the 0.5.8 work plus the new app icon; 0.5.8 was never published) is installed from the local release build and runs with automatic regions and a 1980 | 3720 | 1980 layout.

The user's main game refuses `RegionHook.dll` by its own protection; a clean retry showed no Windows mitigation policy blocking it. Do not try to get past that. ## Known limits

- Without a Force rule, apps get only the outside fit: exclusive fullscreen is never confined, and a borderless game that resizes itself back is left alone after three moves. The borderless fit is checked only by self-tests on hidden in-process windows, not yet against a real game or a browser's fullscreen.
- The repository became public on October 11, 2026. Every earlier Actions run failed on account billing; whether public runs succeed has not been observed yet. The manual route is `scripts/release.ps1 -Publish`.
- Apps that are not DPI-aware are confined at the wrong size above 100% scaling: the native hook reports physical region coordinates to a process whose coordinates Windows scales.
- The first automatic update can only be observed once a release newer than the installed 0.5.6 exists.

## In 1.1.3 (published October 15)

Published by CI as `1.1.3` (run 38656502182). Not yet installed on the development computer, and the takeover of a component loaded by 1.1.2 is not yet confirmed live. Notes: [releases/1.1.3.md](releases/1.1.3.md). Evidence: [testing.md](testing.md), "Reconnecting to a component in a browser window".

- **Reconnecting to a browser window** (user report: every update needed the browser with a Force rule reopened): on reuse, `HookHost.cpp` `ExistingSubclass` required the worker's window-procedure subclass, which a `Chrome_WidgetWin_*` window never gets since 1.1.0, so every reconnection failed with Windows error 1400. It now accepts such a window. Reconnection hands over control, not code: the app keeps the component's code it loaded until it restarts (hot-swapping a loaded DLL is not attempted).

## In 1.1.2 (published October 14)

Published by CI as `1.1.2` and installed on the development computer. Notes: [releases/1.1.2.md](releases/1.1.2.md). Evidence: [testing.md](testing.md), "Robustness fixes" and "Live outside-fit suite".

- **Robustness fixes** from an ECC review (C#, silent failures, native): a not-responding borderless window is kept and journaled until its title bar comes back; App rules Save/Ignore/Restore re-inspect the listed window (`MainForm.StillOpen`); briefly locked settings files are retried (`XmlFile.OpenRead`); the clip host never destroys a window it could not un-parent; both seqlock readers retry with yields; silent failures are logged.
- **Removing a rule** (user report: the app was handled again only after pause and resume): `RegionService.RemoveRule` released the matching processes for the session; it now readmits them at once (`Engine.Readmit`), as README already described.
- **Helper commands with a byte order mark**: `HookHost.cpp` `ReadCommands` skips a leading UTF-8 BOM. A .NET controller whose input encoding is UTF-8 (a UTF-8 console, or Windows set to UTF-8 for non-Unicode programs) sent one before its first command, which then failed as "Unknown command"; a pause's OFF was lost and a Force app stayed confined until the next tick.
- **Live outside-fit suite**: `tests/test-outside-fit.ps1` with `tests/fixtures/TargetWindow.cs` (built at test time into `test-results`, never packaged; user preference: test tools stay out of the app) drives a copy of the engine through its public API against a stand-in window in another process: every rule, automatic handling, rule removal, a not-responding window and a killed controller. It refuses to run while DisplayWeave runs.
- **Known issue, not fixed** (kept failing on purpose in the suite): an app that maximizes itself while Force confines it is left un-maximized at region size on pause; the hook's `RestoreWindow` restores the placement saved at attach. A Force app that did not maximize gets its frame and place back. A Force app that went borderless fullscreen while confined also gets a correct state back (scenario added after the 1.1.2 push, passing), so the common game path is unaffected.
- **Release notes**: `docs/releases/<version>.md` for every version. CI's `version` job fails a new version without one, and the `release` job publishes it (`--notes-file`, then GitHub's generated changelog link). Every published release from 0.5.6-preview to 1.1.1 was edited to carry its notes (October 14; immutable releases allow it).
- The user's installed 1.1.1 was closed with `--exit-for-update` at their request for the live run, then started again.

## Shipped in 1.1.0 (committed October 14)

Committed on `main` as `1.1.0`; CI builds a full, latest release after the `release`-environment approval (not yet published or verified — do not report it as available until it is). Managed self-tests pass (20 + 70 + 14 + 34), as do native policy and IPC on x64 and x86.

- **App rules list apps, not windows** (user request): `WindowManager.ListApps`/`GroupByApp` list one entry per program, stable window class and Store app ID, which is how rules match. The user's browser shows once, named from the program's file description, instead of once per window title. Dragging onto a window makes that window the entry's target.
- **Fullscreen Chromium refit from the move event** (`FullscreenController.RefitNow`, replacing `RefitsAtOnce`): a fitted window is moved back without a full tick. A Chromium window entering fullscreen asks for a tick at once. A fitted, frameless Chromium window that something else moves elsewhere stays fitted.
- Measured with an engine harness (`RegionService` plus `MaximizeWatcher`, scoped by the executable filter to a renamed copy of the user's browser), 1.0.5 against the new code, with the time the window spent away from its region:

  | Event | Clean (nothing else loaded) | With a third-party display tool's DLL in the browser |
  | --- | --- | --- |
  | Entering fullscreen (F11) | 92 ms → 32 ms | 186 ms → 23 ms |
  | Losing focus | 8–25 ms → 7–8 ms | left 60 px over each neighbor → 3–6 ms |
  | Regaining focus | 5–31 ms → 7–10 ms | 87–262 ms → 8–11 ms |
  | Restack | about 4 ms → about 4 ms | about 4 ms → about 4 ms |

  The third-party tool moves the browser into its own, slightly wider regions; 1.0.5 then stopped treating the window as fullscreen. Its driver keeps loading the DLL into new processes after its service stops, until Windows restarts. Pixel scans showed the fitted window filling its region in every run; gaps the user saw came from the third-party tool placing the user's own browser, and later from that browser restored as an ordinary window over the region.
- The flash cannot be removed from outside: the browser moves its own fullscreen window over the monitor on every focus change, and DisplayWeave only learns of it afterwards. Loading anything into the browser to change that was not pursued.
- **Optional region in App rules** (ships regardless of flags). A Force or Maximize rule's region is now opt-in: the App rules page has a "Pin to a specific region" checkbox (step 2); unchecked, the app is handled in whichever region it is currently in, like automatic handling, with the rule's mode (inject for Force, outside fit for Maximize). Borderless and Centered still require a region. `RegionService.Assign` takes `-1` for "no pin" (empty `ZoneId`); `TickWindows`/`ReturnUnruledMaximized`/the session tick route a pinless Force/Maximize rule through the automatic current-region path; a rule that pins no region is never reported as a missing-region problem, but a pinned rule whose region is gone still is. Self-test added.
- **Inject by default** (opt-in with `DISPLAYWEAVE_INJECT_DEFAULT=1`; off by default). Automatic handling injects eligible apps into their current region instead of fitting from outside, and the browser becomes eligible (implies the Chromium gate). Auto-skips the risky: shell/folder and the Battle.net launcher are never eligible, a game whose protection refuses the hook (or any app that faults) falls back to the outside fit, and the Explorer/shell guard is never lifted. Rules still override. The shipped default stays outside-fit. Not yet tested live for coverage beyond the browser.
- **Force-Chromium gate** (opt-in with `DISPLAYWEAVE_FORCE_CHROMIUM=1`; off by default). Drops the Chromium outside-only guard on both layers so a Force rule attaches the window-message hook to the browser: managed `OutsideOnlyReason` skips its Chromium clause, and native `ValidateNonShellTarget` skips `RS_IsChromiumWindowClass` (via `RS_ForceChromiumEnabled`). `RS_IsChromiumWindowClass` itself is unchanged, so its policy self-test still passes. The Explorer/shell guard is never lifted on either layer. This reproduces the 0.5.6 crash on purpose (Chromium self-terminates when its window handling is hooked); it is a confirmation experiment for a throwaway browser profile, not a fix, and the user chose it (2026-10-14) over building the display-bounds-only inject. Automatic mode still fits Chromium from outside regardless of the flag; only an explicit Force rule injects. **Live result 2026-10-14:** injecting into Chrome WORKED (fullscreen confined, no crash); VS Code (Electron) CRASHED. Cause found: RegionHook swaps the window procedure (`EnsureWindowSubclass` → `SetWindowLongPtrW(GWLP_WNDPROC)`), which Chromium/Electron anti-tamper kills; Chrome only tolerated it by luck. **Metrics-only for Chromium (coded, compiles, not yet deployed/tested):** `EnsureWindowSubclass` now returns ready without swapping the wndproc for `RS_IsChromiumWindowClass` windows, so Chromium/Electron are confined by the monitor + `SetWindowPos` hooks alone (no window-handling hook). Needs a live test that confinement holds without the subclass. Gate fix 2026-10-14: the native preflight (`RS_ForceChromiumEnabled` in HookHost.cpp) only checked `DISPLAYWEAVE_FORCE_CHROMIUM`; it was made to honour `INJECT_DEFAULT` too. **Then reverted on the managed side (see below), so the native gate now honours a flag the managed side no longer passes for Chromium — harmless but inconsistent; align `RS_ForceChromiumEnabled` back to `FORCE_CHROMIUM` only on the next native rebuild (blocked while Chrome/VS Code hold `RegionHook.dll`).**

Live result 2026-10-14: metrics-only did NOT stop the VS Code crash. VS Code and Chrome both report window class `Chrome_WidgetWin_1`, so the metrics-only (no-subclass) path applied to VS Code and it still crashed. Its Crashpad minidumps show `EXCEPTION_BREAKPOINT` (int3) faulting inside `Code.exe` itself at a fixed offset — a deliberate abort in VS Code's own Chromium/Electron code (a tamper check or a CHECK on the spoofed monitor data). Chrome's build does not reach it; the two are indistinguishable from outside. Not pursued further (would require bisecting on a throwaway VS Code, and no safe fix is in reach).

Decision 2026-10-14: inject-by-default must NOT auto-load into browser/Electron windows, because some self-terminate and they can't be told apart from Chrome. `ForceChromium` is now `DISPLAYWEAVE_FORCE_CHROMIUM` only (no longer implied by `INJECT_DEFAULT`): under `INJECT_DEFAULT` the browser/Electron class keeps the outside fit; loading into a specific one is explicit opt-in via `DISPLAYWEAVE_FORCE_CHROMIUM` plus a rule. Managed build and all self-tests pass (20+70+14+34).

Follow-up 2026-10-14 (user: "FORCE_CHROMIUM on by default, leave the DLL injection to rules"): the Chromium gate is now **open by default**. `ForceChromium` in `FullscreenController.OutsideFit.cs` is `GetEnvironmentVariable("DISPLAYWEAVE_FORCE_CHROMIUM") != "0"` — on unless set to `0` (the off-switch). So a Force/inject rule loads a browser/Electron window with no env var. Auto-injection is still held back: `TickWindows`'s inject-default branch gained `&& !ChromiumWindowProtection.IsChromiumWindow(...)`, so `INJECT_DEFAULT` never auto-loads the browser/Electron class even with the gate open — only a rule does. The native preflight needs no rebuild: `AttachCore` (`FullscreenController.Sessions.cs`) now sets `DISPLAYWEAVE_FORCE_CHROMIUM` in the helper's environment to match `ForceChromium`, so the native gate follows the managed decision. `RS_ForceChromiumEnabled` in HookHost.cpp is left as-is (honours both flags) — now moot, since the managed side always passes the explicit flag; the earlier "align on next native rebuild" note no longer blocks anything. VS Code (Electron) still self-terminates if a rule injects it (its own int3), so that stays an explicit per-app choice. `RuleTests.Exclusions.cs` updated to the new policy. **Next (not started): multi-window** — confine every top-level window of an injected process to its own current region (the hook/protocol handle one window per process today); rules apply to the whole app. Larger native rework (protocol/monitor virtualization).
- **Clip-host experiment** (`FullscreenController.ClipHost.cs`, opt-in with `DISPLAYWEAVE_CLIPHOST=1`; off by default, no behaviour change when off). Instead of chasing the fullscreen Chromium window, `FitMaximized` reparents it (`SetParent`) into a borderless, region-sized window DisplayWeave owns. Windows clips a child to its parent, so the browser can no longer paint past the region and there is nothing to chase. `ReleaseHost` un-parents the window before destroying the host on every teardown path (`ReturnToMonitor`/`Pause`/`Dispose`/`LeaveFittedWindows`/the `maximized.Remove` paths), because destroying a parent destroys its children — the one real risk is that a hard kill of DisplayWeave while a window is clipped would take that browser window down with the host. A self-test verifies reparent-then-release restores the window and never destroys it. Not yet tested live. Known caveats to measure: cross-process keyboard focus is not handled (mouse first), content momentarily laid out at monitor width is clipped to the region during Chromium's re-assert instead of ballooning past it, and host z-order against neighbours. (Superseded by the gate-default-on follow-up above: with the Chromium gate open, a Force rule now reaches Chromium through `AttachCore` rather than `FitFromOutside`. The clip host remains an independent, still-untested alternative that needs no injection.)
