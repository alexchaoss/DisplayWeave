Fixes found by a code review and by new live tests against a stand-in app.

- **Removing a rule takes effect at once.** The app goes straight back to automatic handling (or to being left alone when automatic handling is off). Before, it stayed out of handling until you paused and resumed.
- **Borderless in region:** a window that is not responding when handling pauses, its rule changes or DisplayWeave exits keeps its place on the recovery list and gets its title bar back once it responds, or at the next start. Before, it could stay without its title bar for good.
- **App rules:** Save, Ignore and Restore check that the listed window still belongs to the same app. A closed app's window handle that Windows reused for another app no longer gets that app's rule.
- **Settings:** a settings file that a backup or antivirus scan holds open for a moment is read again instead of being treated as unreadable, which could replace your settings with defaults on the next save.
- **Force fullscreen:** the native helper accepts commands that start with a UTF-8 byte order mark. Before, the first command was rejected, so pausing could leave the app confined until the next check.
- **Force fullscreen:** the component retries reading its settings while DisplayWeave is updating them, instead of failing to attach until the app restarted.
- Failures that used to be silent are now written to the activity log: a window that could not be moved back, an unreadable recovery list, and window-move notifications that Windows did not start.

**Known issues**

- An app that maximizes itself while a Force fullscreen rule confines it is left un-maximized at its region's size when handling pauses. Maximize it again.
- Restart as administrator still starts the app from your user-writable install folder; see SECURITY.md, "Known limits".
